# VieNeuTTS-Android — Sub-project 1: TTS Engine Core — Design

Status: approved (architecture section confirmed by user 2026-07-23)
Scope: **engine only**. The EPUB reader + playback UI (speed control, pinch,
bookmarking, background playback, voice picker, etc.) is a separate
sub-project and gets its own spec once this one is built and validated on
device.

## 1. Goal

Prove that VieNeu-TTS (currently a Python package built on ONNX Runtime CPU
+ a Rust G2P engine) can run natively on Android, producing audio for
arbitrary Vietnamese/English text using one of VieNeu-TTS v3 Turbo's 14
built-in preset voices — with no PyTorch, no network calls, fully offline.

Success criteria: an Android library module (`:engine`) that exposes
`synthesize(text: String, voice: String): ShortArray` (or equivalent PCM
buffer), backed by a sample app with a single screen (text box, voice
picker, Play button), producing audio on a real/emulated Android device
that is recognizably correct Vietnamese speech when compared by ear against
the same input run through the existing Python CPU/ONNX build in
`/workspaces/my-personal-project/VieNeu-TTS`.

Voice cloning, denoising, and streaming playback are explicitly **out of
scope** for this sub-project (see §7).

## 2. Feasibility findings (why this is buildable)

Grounded in reading the actual VieNeu-TTS source (not the README marketing
copy) on 2026-07-23:

- **Phonemizer (`sea-g2p`)** is not an espeak-ng wrapper. It's a
  self-contained **Rust crate** (Apache-2.0, source at
  github.com/pnnbao97/sea-g2p), `crate-type = ["cdylib"]`, depending only on
  `regex`, `fancy-regex`, `once_cell`, `memmap2`, `rayon`,
  `unicode-normalization` — all portable, standard crates with no
  Android-hostile dependencies. `ldd` on the installed `.so` shows only
  libc/libgcc/libpthread/libdl — no espeak-ng linkage. The 48 MB
  `sea_g2p.bin` is a memory-mapped dictionary/model file, not code.
- **Default-voice synthesis is already PyTorch-free.**
  `src/vieneu/_v3_turbo_engine/onnx_runtime_lite.py` (`OnnxV3LiteEngine`) is
  pure NumPy + `onnxruntime`, used specifically so CPU synthesis doesn't
  need PyTorch. This is the code path to port, not the PyTorch engine in
  `inference_v3_turbo.py` (that one backs voice cloning/denoising and is
  intentionally out of scope — see §7).
- **Model payload is small enough to bundle**: `onnx_int8/` backbone
  (prefill + decode_step + acoustic_cached graphs, tied-weights npz) ≈
  166 MB; codec decode-only files (`moss_audio_tokenizer_decode_*`) ≈ 45 MB
  (the 44.5 MB `encode.onnx`/`encode.data` are only needed to encode a
  *reference* clip for cloning — skip them); `sea_g2p.bin` ≈ 48 MB. Total
  ≈ 260 MB, verified via the HF Hub API file listings for
  `pnnbao-ump/VieNeu-TTS-v3-Turbo` and
  `OpenMOSS-Team/MOSS-Audio-Tokenizer-Nano-ONNX`.
- **Licensing**: VieNeu-TTS, sea-g2p, the v3-turbo model weights, and the
  MOSS codec are all Apache-2.0 (confirmed via HF Hub API `cardData.license`
  and the GitHub repo license endpoint). No redistribution blocker for
  bundling model files inside an app.

## 3. Architecture

Two new Gradle modules in a new git repo, `VieNeuTTS-Android/`:

```
VieNeuTTS-Android/
├── engine/                    # Android library module (Kotlin + JNI)
│   ├── src/main/kotlin/.../TtsEngine.kt
│   ├── src/main/jniLibs/arm64-v8a/libsea_g2p_uniffi.so
│   └── src/main/assets/       # onnx_int8/*, codec decode-only files, sea_g2p.bin
├── app-sample/                # single-screen harness: text box, voice picker, Play
└── rust/sea-g2p-android/      # fork of sea-g2p + uniffi interface definition
```

`app-sample` depends on `engine`; `engine` is what sub-project 2 (the EPUB
reader app) will later depend on unchanged. This split exists specifically
so sub-project 2 does not require re-touching the native/ONNX code.

### 3.1 Component decisions

| Concern | Decision | Why |
|---|---|---|
| G2P (text → phonemes) | Fork `sea-g2p`, add an Android-target crate reusing its existing `g2p`/`vi_normalizer`/`punc` modules, cross-compiled with `cargo-ndk` for **arm64-v8a only**, bindings generated by **uniffi-rs** | uniffi auto-generates the Kotlin↔Rust glue (String marshalling, memory) instead of hand-written JNI, which is the highest-risk-of-silent-bugs part of any Rust-on-Android integration. This is the same pattern Mozilla uses to ship Rust in Firefox for Android. |
| TTS inference | `onnxruntime-android` (official Maven artifact `com.microsoft.onnxruntime:onnxruntime-android`) running the three exported graphs (`vieneu_prefill.onnx`, `vieneu_decode_step.onnx`, `vieneu_acoustic_cached.onnx`) | Official, mobile-targeted, no custom native build needed for this part — Gradle dependency only. |
| Sampling / orchestration | Kotlin, ported line-for-line from `onnx_runtime_lite.py` (softmax, top-k/top-p, repetition penalty, embedding lookups, prompt building, KV-cache bookkeeping between ORT calls) | No existing library does this; it's bespoke glue that has to be reimplemented once regardless of platform. |
| Audio output | `android.media.AudioTrack`, one full `write()` per synthesized utterance | Matches the "no streaming in MVP" decision (§7) — avoids doing playback threading and inference threading at the same time before the inference loop itself is proven correct. |
| ABI target | **arm64-v8a only** | Covers real Android phones and Android Studio emulator system images on Apple Silicon Macs (the user's Mac is Apple Silicon, confirmed via this devcontainer's aarch64 host arch) — no need for x86_64 build in this sub-project. |

## 4. Data flow

```
text (Kotlin String)
  → uniffi call → Rust sea-g2p core → phoneme string (back to Kotlin)
  → Kotlin: build prompt tokens (port of prompt_v3_turbo.py — pure logic, no native code needed)
  → onnxruntime-android: run vieneu_prefill.onnx once → initial hidden state + KV-cache tensors
  → Kotlin loop, once per output frame:
      run vieneu_decode_step.onnx, feeding the current KV-cache as input
        and receiving updated KV-cache + logits as output
      sample next audio-code frame (softmax/top-k/top-p/repetition-penalty, in Kotlin)
      stop when eos_id is sampled or max_new_frames is hit
  → stack all sampled codes → run vieneu_acoustic_cached.onnx once → PCM float32 @ 48kHz
  → AudioTrack.write(pcm) → play
```

This mirrors `OnnxV3LiteEngine`'s control flow exactly (see
`src/vieneu/_v3_turbo_engine/onnx_runtime_lite.py` in the VieNeu-TTS repo),
just with NumPy replaced by Kotlin arithmetic and ORT's Python API replaced
by `onnxruntime-android`'s Java API.

## 5. Error handling

Kept intentionally minimal for a dev/test harness, not a shipped app:

- If the native G2P library or an ONNX model fails to load, the sample app
  shows the raw exception message in a text view. No retry/fallback logic.
- No input validation beyond "non-empty text" — this is a synthesis
  correctness harness, not a hardened app.

## 6. Testing

- Instrumented test on a real Android environment (device or emulator),
  reached via ADB over the Tailscale connection already established between
  this devcontainer and the user's Mac (`nghia`, 100.79.51.16).
- Validation method: run the same input text through (a) this Android
  build and (b) the existing Python CPU/ONNX build in
  `/workspaces/my-personal-project/VieNeu-TTS` (already set up and
  verified working as of 2026-07-23), and compare by ear — plus sanity
  checks on sample rate (48kHz) and output duration being non-zero and
  proportional to input length.
- No automated audio-similarity scoring in this sub-project — that's a
  nice-to-have, not a blocker.

## 7. Explicitly out of scope (for this sub-project)

- **Voice cloning / reference-audio enrollment / denoising.** Per
  VieNeu-TTS's own docs these require the PyTorch engine (the ONNX speaker
  encoder's fbank front-end also depends on `torchaudio`). Only the 14
  built-in preset voices are supported. Revisit later if cloning becomes a
  real product requirement — the denoiser and speaker-encoder ONNX graphs
  do exist and are individually portable, but the fbank/mel front-end would
  need a from-scratch DSP port first.
- **Streaming playback.** MVP generates a full utterance, then plays it.
  Chunked/streaming generation (mirroring `infer_stream` in the Python
  code) is a follow-up once the non-streaming path is proven correct on
  device — it adds concurrent decode+playback threading that would
  otherwise confound debugging the inference port itself.
- **EPUB parsing, reading UI, playback controls, pinch gestures, bookmarks,
  background/notification playback.** All of that is sub-project 2, to be
  spec'd separately once `:engine` is validated.
- **x86_64 / emulator-on-Intel builds.** Only arm64-v8a, per §3.1.

## 8. Decisions log

Captured from the brainstorming session (2026-07-23):

1. Split into two sub-projects (engine core, then reader app) rather than
   one combined spec — reduces risk by validating the highest-uncertainty
   part (native TTS port) before investing in UI.
2. `:engine` is a proper Android library module + minimal sample app, not
   a single monolithic app — so sub-project 2 can depend on it unchanged.
3. No streaming in the MVP engine — simplifies validating the
   inference/KV-cache loop before adding playback concurrency.
4. Test target is an Android emulator, reached from this devcontainer via
   Tailscale to the user's Mac (arm64-v8a system image, matching real
   devices).
5. Rust↔Kotlin binding via uniffi-rs rather than hand-rolled JNI.
